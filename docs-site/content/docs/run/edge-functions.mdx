## What runs on a schedule

The source lives in `supabase/functions/`. Each function is called by a `pg_cron` job that posts to it over `pg_net`. The schedules are defined in `supabase/migrations/`, so applying the migrations creates them; you do not schedule anything by hand.

| Job | When (UTC) | Function |
|---|---|---|
| `send-event-reminders-daily` | 15:00, 16:00 and 17:00 daily | `send-event-reminders` |
| `send-supper-reminders-daily` | 15:00, 16:00 and 17:00 daily | `send-supper-reminders` |
| `send-serving-reminders-hourly` | Every hour, on the hour | `send-serving-reminders` |
| `send-serving-monthly-broadcast` | 15:00 on the 1st | `send-serving-reminders` |
| `clean-up-expired-data-nightly` | 09:00 daily | `clean-up-expired-data` |

`refresh-church-records` is the exception: no migration schedules it. See [refresh-church-records](#refresh-church-records).

Each function works through every active church in turn and filters every query on that church. A church an operator has suspended gets no reminders and no clean-up; see [Add a church](/docs/run/add-a-church#suspend-a-church).

### send-event-reminders

Emails the people who replied Yes or Maybe to an event, before each date of the event, as many days ahead as the event chose. It records what it sent, so a rerun never sends twice. The 15:00 firing sends; the 16:00 and 17:00 firings finish what a failed or cut-off firing left.

### send-supper-reminders

Emails the people at each Supper club table the day before their supper, in the church's time zone: the time, the host, the address and who is coming. It skips anyone who said Not going or turned Supper club emails off, and groups with the Supper club off. It records what it sent, so a rerun never sends twice, and a moved supper is reminded on its new date. The 15:00 firing sends; the 16:00 and 17:00 firings finish what a failed or cut-off firing left.

### send-serving-reminders

Runs in two modes, one per job:

- **Hourly.** Reminds the people on a team's next service date once the team's reminder day and hour have come in the church's time zone. It records what it sent, so a rerun never sends twice.
- **Monthly**, on the 1st. Emails each team the service dates that still need people. A team whose dates are all covered gets nothing.

Serving emails carry links that act without signing in when `SERVING_LINK_SECRET` is set and the link mode is `signed`. See [Environment variables](/docs/run/environment#edge-function-secrets).

### refresh-church-records

For every church connected to its church records, copies the details of people changed there since the last run, and of linked people not copied yet, into two42, following the church admin's settings. It lists linked people who became inactive or can't be found under **Needs review**, and changes nothing else about them. Then it reads the families of linked people: it replaces the household suggestions the church admin confirms on the **Households** tab, copies each confirmed household's address and home phone under the same settings, and, while the church suggests children, updates the children suggested to each confirmed household and fetches the photo of a child a household added. When the church's key isn't allowed to read families, it copies people as usual and skips households, which the **Households** tab reports; any other error reading families fails that church's refresh. Running out of time while reading families, or fetching children's photos, cuts the refresh short like running out of time copying people, and the last suggestions stay. It stops starting people after 90 seconds, shared by every church in the run; the rest wait for the next run, which carries on where this one stopped and copies people still waiting first. Each day's run starts one church further down the list, so a church that uses up the time doesn't keep the others waiting. A run that ran out of time answers 500 and lists, under `cutShort`, each church it stopped partway through and, under `notStarted`, each it never reached. A church whose refresh was already running, a **Refresh now** for example, is skipped and listed under `busy`, and the run answers 500 too. A church where some people's copy failed is listed under `copyFailed`, and the run answers 500; the next run copies those people again. Each listed church's **Last refreshed** stays on its last finished refresh. A church admin's **Refresh now** runs the same code. See [Imports](/docs/administer/imports#copy-details-from-your-churchs-records).

It needs `RECORDS_KEY_SECRET` in the edge function secrets, the same value as the app's; without it the function answers 200 and does nothing, and with a value that isn't a 32-byte base64 key it answers 500 and does nothing. Before it opens any church's key it checks that the runtime refuses a request to a loopback address, and stops with a 500 if it doesn't, saying so in the response.

No migration schedules it. To run it nightly, add a `pg_cron` job in the SQL editor that posts to it the way the other jobs do, for example at 08:30 UTC:

```sql
select private.schedule_edge_reminder(
  'refresh-church-records-nightly',
  '30 8 * * *',
  '/functions/v1/refresh-church-records',
  '{}'::jsonb,
  120000
);
```

The scheduled-jobs check doesn't know this job: it counts every response in the first 15 minutes of each hour against the jobs it expects. Scheduled at half past, the job's responses fall outside those windows; scheduled on the hour, the check reports an extra response that night, and a non-200 when the run was cut short. Read this job's results in `net._http_response` instead.

### clean-up-expired-data

Deletes data that has expired, one church at a time. It never deletes a church.

| What | When it is deleted |
|---|---|
| Declined access requests | 90 days after they were declined |
| Approved access requests whose setup link was never used | 90 days after the link expired. A church's first admin's request is kept. |
| Household invites never accepted | 90 days after they were sent, or created if never sent, unless a pending request or a live setup link still uses them |
| Group invite links | 90 days after they were revoked or expired |
| Feedback | 12 months after it was sent |
| Prayer requests | Only when the church admin has chosen a period under **Old prayer requests** in the church settings: 6, 12 or 24 months after posting. Unset, prayer requests are kept. |
| Serving, event and Supper club reminder records | 35 days after the date they cover |
| Usage counts | 13 months after the day they count |

### When Resend limits sending

Every function sends through one helper. When Resend answers that the rate limit was exceeded, it waits the time Resend states and sends the same email again under the same idempotency key, up to three tries, so nobody gets it twice. A rate limit that outlasts those tries, or Resend's daily or monthly quota, stops a reminder run's sending. For event and Supper club reminders, a later firing in the same day's cycle (16:00 or 17:00 UTC) sends what it left once the limit has cleared, and nothing carries past 17:00 UTC into the next day's cycle. For the hourly serving reminders, each later hourly firing sends what it left once the limit has cleared, until 22:00 in the church's time zone, and nothing carries into the next day. A limit that lasts past the day's last firing leaves those reminders unsent. The monthly serving broadcast does not stop: it counts an email still refused after the helper's tries as failed, moves on to the next person, and no later firing resends it. See [When Resend limits sending](/docs/run/email#when-resend-limits-sending).

## Set the function secrets

The functions read their own secrets, set with `npx supabase secrets set NAME=value` or under Edge Functions → Secrets in the dashboard. The full list is in [Environment variables](/docs/run/environment#edge-function-secrets). Supabase injects `SUPABASE_URL` and the service key; do not set them.

## Create the Vault secrets

The `pg_cron` jobs read the project URL and a service key from Supabase Vault by name, because neither can be committed. **Both are required.** Until they exist, every job still runs on schedule and fails, and nothing in the app shows it.

Create them once, in the SQL editor:

```sql
select vault.create_secret('https://<project-ref>.supabase.co', 'cron_project_url');
select vault.create_secret('<the secret key>', 'cron_service_role_key');
```

The functions answer `401` to any caller whose `Authorization: Bearer` header is not one of the project's service keys, so the Vault key must be one of them.

## Check that the jobs ran

Run these in the SQL editor:

```sql
select name from vault.decrypted_secrets
 where name in ('cron_project_url', 'cron_service_role_key');   -- expect both rows

select j.jobname, d.status, d.return_message, d.start_time
  from cron.job_run_details d join cron.job j using (jobid)
 order by d.start_time desc limit 10;                            -- did each job run?

select status_code, created
  from net._http_response order by created desc limit 10;       -- expect 200s
```

A `401` means the Vault key is not one of the function's service keys.

The same check, as one query, is [`scripts/check-scheduled-jobs.sql`](https://github.com/cwaits6/two42/blob/main/scripts/check-scheduled-jobs.sql). It covers every firing in the six hours before it runs, because `pg_net` keeps responses for six hours. This repository runs it against its hosted project every six hours, at 03:30, 09:30, 15:30 and 21:30 UTC, from [`.github/workflows/scheduled-jobs-check.yml`](https://github.com/cwaits6/two42/blob/main/.github/workflows/scheduled-jobs-check.yml), which uses the same `SUPABASE_PROJECT_REF`, `SUPABASE_ACCESS_TOKEN` and `SUPABASE_DB_PASSWORD` secrets as the deploy workflow. The workflow fails, which sends GitHub's failed-run notification, when a job did not run, a response was not a 200, or a firing's responses are missing.

## Deploy the functions

```bash
npx supabase functions deploy send-event-reminders send-serving-reminders clean-up-expired-data send-supper-reminders refresh-church-records
```

Deploy them on every update, before applying the migrations. That is the order this repository's CI uses; see [Deploy from GitHub Actions](/docs/run/deploy#deploy-from-github-actions).
